# Database schema

PostgreSQL. Migrations are in `backend/migrations/` and are the source of truth; this page explains them. Conventions: UUID primary keys, `timestamptz` everywhere, every integrity rule enforced **in the database** as well as in the application.

```mermaid

    users ||--o{ document_members : "belongs to"

    documents ||--|| document_states : "body"

    documents ||--o{ comments : "discussion"
    users ||--o{ document_versions : "saved by"
    users ||--o{ comments : "written by"

    users {
      uuid id PK
      text email "lower-case, unique"
      text display_name

      timestamptz created_at
    }
    sessions {
      uuid id PK
      uuid user_id FK
      bytea token_hash "SHA-256, unique"
      timestamptz expires_at
      text user_agent
    }
    documents {
      uuid id PK "client-generated"
      text title
      timestamptz updated_at
    }
    document_members {
      uuid document_id PK_FK
      uuid user_id PK_FK
      document_role role "owner / editor / viewer"
    }
    document_states {
      uuid document_id PK_FK
      bytea state "merged Yjs update"
    }
    document_versions {
      uuid id PK
      uuid document_id FK
      uuid created_by FK "null = automatic"
      version_kind kind "manual / auto"
      text label
      bytea state
    }
    comments {
      uuid id PK
      uuid document_id FK
      uuid author_id FK
      text body
      text quote "copy, not an anchor"
      boolean resolved
    }
```

## Tables

### `users`
| Column | Notes |
|---|---|
| `email` | Stored lower-cased; a `CHECK (email = lower(email))` makes a non-normalised insert impossible. Unique index. |
| `password_hash` | `scrypt$N$r$p$salt$hash` (base64). The cost is recorded per hash so it can be raised later without invalidating old hashes. The password itself is never stored. |

### `sessions`
Server-side sessions so access can be revoked at once. `token_hash` is the SHA-256 of the 256-bit random cookie value: a database leak does not leak usable sessions. Expired rows are removed opportunistically on login. Rows cascade-delete with their user.

### `documents`
Metadata only. The `id` is generated by the **browser** (so a document can be created offline) and registered later with an idempotent `PUT`. The body is **not** here.

### `document_members`
The authorization table: **no row = no access**. The owner is a member with role `owner`. A partial unique index `document_members_one_owner (document_id) WHERE role = 'owner'` guarantees exactly one owner per document (tested by trying to insert a second).

### `document_states`
One row per document: the whole merged Yjs state as a single encoded update in `bytea`. Rich text is **never** stored as HTML or JSON rows; that would make a lossless CRDT merge impossible. Written (debounced) by the realtime server in the same transaction that bumps `documents.updated_at` and, when due, adds an automatic version.

### `document_versions`
Frozen full Yjs states. `kind = 'manual'` rows are saved by a user (`created_by` set) and never pruned; `kind = 'auto'` rows are checkpoints created at most every `AUTO_VERSION_INTERVAL_MS` and trimmed to the newest `AUTO_VERSIONS_KEPT`. `created_by` is `ON DELETE SET NULL`.

### `comments`
Conversation about a document, deliberately outside the Yjs structure. `quote` is a **copy** of the selected text (≤ 300 chars), not a live anchor.

## Retention and deletion

* Deleting a document cascades to its members, state, versions and comments (tested).
* There is no user-deletion feature; the foreign keys are nevertheless defined (`CASCADE` for sessions / memberships, `SET NULL` for authorship of versions and comments).
* `document_states` and `document_versions` hold the only server-side copy of document content: **back them up**.

## Migration runner

`backend/src/db/migrate.ts`:

* applies files named `NNN_name.sql` in order, **each in its own transaction** (a failing migration leaves nothing half-applied; tested);
* records `version`, `name`, SHA-256 `checksum` and time in `schema_migrations`;
* refuses to run if an already-applied file was edited (history is append-only; tested);
* takes a PostgreSQL advisory lock so two servers starting together do not race.

```bash
npm run migrate          # apply pending migrations (uses DATABASE_URL, or the local dev database outside production)
```

## Seed / demo data

`npm run seed` creates three demo accounts (`alice@`, `bob@`, `vera@example.com`, password `demo-password-123`) and one shared document. It is idempotent and **refuses to run with `NODE_ENV=production`**.

## Inspecting the dev database

With `npm run dev:db` running (port 54320), any PostgreSQL client works:

```
postgres://localsync:localsync-dev-only@127.0.0.1:54320/localsync
```

(Credentials of the bundled development database only; they protect nothing of value and must not be reused.)
